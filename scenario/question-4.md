# 情境實戰測驗 題目四：新服務串接 ELK/EFK

> 試想已有一組 ELK/EFK 日誌服務集群，而今日有一新服務上線並且串接日誌紀錄，讓開發者
> 能夠透過 Kibana 進行線上錯誤排查，你將如何將日誌檔內容串接至 ELK/EFK 系統？
> 考量的細節是什麼？

## 這題的邊界

叢集已經存在，而且正在服務其他團隊。所以要做的不是設計一套日誌系統，是把一個新服務
接進去、並且不弄壞既有的東西。

第一件事是去找叢集的維運者，確認索引命名規範、每日可承受的資料量、
以及有沒有既有的欄位約定。新服務接入撞爆既有叢集的情況並不少見，而原因通常很單純：
沒有人先問一聲。

## 六個階段各自的決定

| 階段 | 決定 | 理由 |
|---|---|---|
| 收集 | 應用只寫 JSON 到 stdout／stderr，不碰檔案輪替，也不自己送 | 日誌落地與傳輸屬於平台職責 |
| 傳輸 | Fluent Bit 以 DaemonSet 部署，每個 node 一份 | 不必改動每個 Deployment；資源成本隨 node 數走，sidecar 則是隨 pod 數 |
| 解析 | 應用端就輸出結構化欄位，收集端只做補充（k8s metadata、環境標籤） | 在來源做比在管線做便宜且準確 |
| 儲存 | 走既有命名規範的 data stream，上線同時設好 ILM | 沒有 ILM 的索引就是留給別人的帳單 |
| 查詢 | 事先建好 index pattern 與一組給開發者的 saved search | 開發者要能直接開始查，不必自己摸索欄位結構 |
| 維運 | 監控 agent 本身的送出失敗率與 buffer 用量 | 日誌管線斷掉時最不該發生的事，就是沒有人知道 |

如果既有叢集本來就有 Logstash，解析與 enrich 交給它即可。只為了這個新服務再引入一層
Logstash 並不划算，Fluent Bit 的 parser 應付得來。

## 哪裡最容易出事

**應用不要直連 Elasticsearch。** 用 SDK 直接打 ES 看起來最短，代價是 ES 一慢，應用的
執行緒就跟著卡；ES 滿了，日誌就直接消失。而且憑證得散到每一個服務裡。中間隔一層
收集器，這三個問題一次解決。

**Structured logging 順便解掉 multiline。** Stack trace 被逐行拆成幾十筆記錄是接入時最
常見的坑，multiline parser 又難調又脆弱。如果應用直接輸出 JSON、把整個 exception 放在
一個欄位裡，這個問題大部分自然消失。剩下真的無法結構化的舊格式日誌，才用 multiline
規則處理。

**Backpressure 要想清楚。** ES 掛掉或變慢的時候，收集器會發生什麼事？沒有設定的話，
記憶體 buffer 撐爆會開始丟日誌，最壞的情況是 agent 被 OOM kill、連 node 上其他服務的
日誌一起遺失。要設 disk buffer 上限與重試策略，並且明確決定滿了之後是丟棄還是阻塞——
對日誌而言通常選丟棄，但這要是有意識的決定。

**欄位爆炸會拖垮整個叢集。** 如果日誌把不固定的 key 塞成欄位（例如把 user id 當欄位名），
mapping 會無限膨脹，影響的是整個叢集而不只是這個索引。上線前先確認欄位是收斂的，
必要時關掉動態映射。

## 敏感資料

日誌一旦寫進去就很難拿掉。上線前要確認的是：不要記錄完整的授權標頭、身分證字號、
信用卡號、密碼欄位。訂房平台的日誌天生就會經過旅客個資，這一層要在收集端就遮蔽，
不能寄望事後清理。

另外，Kibana 的權限要跟著設。開發者需要的是查自己服務的日誌，給到整個叢集的讀取
權限就過頭了。

## 怎麼算接完

不是「資料有進去」就結束。我會做一次端對端驗證：在服務上故意打一筆 ERROR，然後在
Kibana 用開發者實際會用的查詢方式找到它，並且確認時間戳的時區正確、
`kubernetes.pod_name` 之類的關鍵欄位都在、堆疊追蹤是完整的一筆而沒有散成幾十行。

這件事要讓開發者自己做一次。他們找得到，才算接完。
