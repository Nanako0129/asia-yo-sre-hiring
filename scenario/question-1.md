# 情境實戰測驗 題目一：活動網頁的百倍流量

> 試想臨時有一活動網頁專案將於近日推出，預期推廣期間訪客流量會是平日常態之百倍（或更多）。
> 請簡易描述你將如何確保服務能在推廣期間正常運作？考量的細節是什麼？

## 先講結論

「百倍流量」不是一個容量問題，是一個分類問題。同樣是百倍，讀取流量對 CDN 來說是日常，
寫入流量會直接殺死資料庫。所以開機器之前，先把這場活動的請求分成三類：

| 類別 | 範例 | 處理位置 | 百倍的難度 |
|---|---|---|---|
| 純展示 | 活動頁本體、圖片、文案、倒數計時 | CDN 邊緣，源站看不到 | 低，靜態化就解決 |
| 讀取即時資料 | 剩餘名額、優惠碼庫存數 | 短 TTL 快取 + 邊緣 | 中，要接受數秒誤差 |
| 寫入 | 領碼、扣庫存、建立訂單、付款 | 必須進到源站與資料庫 | 高，這是唯一的真問題 |

活動能不能撐住，取決於第三類的絕對數量，而不是總流量的倍數。

## 動筆之前要問的三件事

**平日常態是多少？** 「百倍」是相對值。平日 10 RPS 的百倍是 1,000 RPS，一台機器的事；
平日 3,000 RPS 的百倍是 30 萬 RPS，是完全不同的工程。沒有這個基準數字，後面的容量規劃
全是猜的。

**這頁到底是什麼？** 三種活動頁的答案完全不同：

| 型態 | 例子 | 核心風險 |
|---|---|---|
| 純行銷落地頁 | 品牌宣傳、內容導購 | 幾乎沒有，CDN 就結束了 |
| 導流頁 | 活動頁本身靜態，但點擊後導入主站搜尋／訂房 | 風險轉移到主站，主站才是要保護的對象 |
| 限量搶購 | 限時折扣碼、限量房型秒殺 | 超賣、寫入熱點、競態條件 |

以 AsiaYo 常見的活動樣態（限量折扣碼、限時房型優惠）來看，多半落在第二與第三類的組合：
活動頁靜態，但「領碼」與「用碼下單」是不折不扣的寫入熱點。

**什麼時候開始？** 如果是整點開跑，所有人會在同一秒湧入，這比「一整天有百倍流量」難十倍。
尖峰的形狀比尖峰的高度更重要。

## 活動前

### 先把活動和主站切開

訂房主站是持續在賺錢的系統，活動是臨時的。兩者共用同一組資源時，活動的尖峰會把主站
一起帶走。

- 活動頁走獨立的 Deployment、獨立的 HPA、獨立的 Ingress 或子網域，不與主站 Pod 混跑
- 設好 requests/limits，讓活動的 Pod 不會在節點上把主站的 Pod 擠爆
- 活動要讀主站資料庫的話，走獨立的連線池或 read replica，不共用主站的連線配額
- 準備一個「一鍵下架活動頁」的開關。最壞的情況下，犧牲活動保住主站是正確的取捨

### 讀取：讓源站看不到那個百倍

目標是九成以上的請求在 CDN 就結束。

- 活動頁靜態化，HTML 本身進 CDN，不要每次回源渲染
- 開 Origin Shield，讓多個邊緣節點的回源收斂成一個，避開快取失效瞬間的驚群回源
- 剩餘名額這類會變動的數字，用獨立的小 API 加短 TTL（3～5 秒）快取，不要為了這個數字
  讓整頁不能快取
- 圖片走既有的 S3 + CloudFront，活動前先把主要資源請求一遍，讓邊緣先有快取

順帶一提，「加幾台 read replica 撐過去」是這題最常見的錯誤直覺。讀取加 replica 確實有效，
但活動的壓力在寫入，replica 一條也幫不上，而且會讓人誤以為已經準備好了。

### 寫入才是要花時間的地方

假設是限量搶購。核心問題只有一個：同一份庫存被同時扣減。

- 「查詢剩餘數量」和「扣減」必須是一個原子操作。分成兩步做，中間就是競態條件，高併發下
  必然超賣
- 資料庫層的悲觀鎖（`SELECT ... FOR UPDATE`）在這種併發下會排隊到超時，樂觀鎖則會產生
  重試風暴。可行的做法是把扣減搬到 Redis 用 Lua script 做原子操作，資料庫做非同步落地
  與最終校驗
- 下單請求帶冪等鍵，重複提交回同一個結果。使用者在搶購時瘋狂點擊是常態
- 庫存採預留制：下單先鎖住 10～15 分鐘，付款完成才真正扣掉，逾時自動釋放
- 訂單建立可以非同步化，先進佇列回「處理中」，下游用固定並行度穩定消費。這是把尖峰
  削平最有效的手段，但代價是使用者搶到之後看到的是「處理中」而不是「訂購成功」——
  這個體驗要先跟行銷和客服談好，不是工程單方面能決定的事

至於虛擬候客室（Queue-it 那類排隊系統），票務業已經是標準配備，效果也確實好。但它要
時間導入、要預算、要改前端流程。臨時專案我不會第一次就上，先用限流加一個說明清楚的
等待頁，把這個選項留給下一次有完整準備期的大檔。

### 別指望 autoscaling 來得及

「上了 Kubernetes 就會自動擴容」在整點開跑的活動裡不成立：

| 環節 | 延遲 |
|---|---|
| HPA 觀察到指標超標 | 15～30 秒（預設 metrics 週期，未調參的情況） |
| Cluster Autoscaler／Karpenter 開新節點 | 1～3 分鐘 |
| 節點加入、拉映像檔、Pod 通過就緒檢查 | 數十秒到數分鐘 |

活動開跑後的前三分鐘，系統是靠現有容量撐的。所以活動前把副本數直接開到目標值，不要等
HPA 反應；節點也提前備妥，提高 min size 或先放 placeholder Pod 佔位。多花幾小時的機器錢，
遠比活動掛掉便宜。

另外，HPA 對 PHP-FPM 這類 I/O bound 的服務用 CPU 當指標會失準。請求全卡在等資料庫時
CPU 是低的，但 worker 其實已經被佔滿了。改用 RPS 或佇列長度。

### 先斷的通常不是應用層

應用層可以無限橫向擴展，它的下游不會。這幾項是我會先看的，不算完整清單：

- **資料庫連線數**。PHP-FPM 每個 worker 佔一條連線，`pm.max_children` × Pod 數就是連線
  總需求。Pod 一擴容這個數字線性上升，很容易撞到 RDS 的 `max_connections`。要嘛加
  RDS Proxy／ProxySQL 做連線池，要嘛在擴容計畫裡把這個乘法算清楚
- **第三方相依**。金流閘道、供應商 API、簡訊服務不會因為我們辦活動就跟著擴容，而且通常
  有自己的 rate limit。提前告知對方活動時間，設好逾時與熔斷，金流慢不該讓整個下單流程卡死
- **快取本身**。ElastiCache 的節點規格與連線數也有上限，熱點 key 會讓單一 shard 過載

### 活動流量長得像攻擊

活動開跑瞬間，大量使用者從相似的網路來源、用相似的 User-Agent、以極高頻率請求同一個
URL。這組特徵跟一次 DDoS 幾乎無法區分，而 WAF 不知道今天有活動。

- 活動前 review rate-based rule 的閾值，針對活動路徑放寬或加白名單
- Bot 偵測規則先切到 count 模式觀察，確認不會誤傷再決定要不要 block
- 準備好在活動中快速調整規則的權限與流程，不要等到使用者在客服信箱抱怨才發現

這條在檢查清單裡很容易被漏掉，因為它不會讓監控變紅 —— 被擋掉的請求在系統看來是「成功
處理」的。

### 壓測要壓在寫入路徑上

對首頁壓測會得到一個很漂亮但沒有意義的數字。要壓的是完整的關鍵路徑：進入活動頁 →
領碼 → 下單 → 付款。用真實的資料量壓，不要用空資料庫；壓到壞掉為止，找出天花板實際
在哪一層。

如果時間真的不夠做完整壓測 —— 臨時專案很常見 —— 至少對「扣庫存」這一個 API 做併發
正確性測試，確認不會超賣。系統慢還能救，賣超了要退款道歉。

## 活動中

降級開關要在活動前就做好，活動中只能開關，不能改 code。臨時改上線是活動期間最危險的
動作。

| 順序 | 關掉什麼 | 保住什麼 |
|---|---|---|
| 1 | 推薦、個人化、評價、相關房源 | 版面還在，功能可用 |
| 2 | 即時剩餘數量改為靜態文案 | 減少一整條讀取路徑 |
| 3 | 排隊機制介入，超額請求回等待頁 | 進到系統的人能順利完成 |
| 4 | 活動頁整個下架 | 訂房主站不受影響 |

回絕流量時要回得體面。帶 `Retry-After` 的 429 加上一個說明清楚的等待頁，比 502 好得多：
使用者看到「活動太熱烈請稍候」會等，看到伺服器錯誤會重整，而重整會讓情況更糟。

監控要看業務指標。活動期間我盯的是每分鐘成功下單數、下單成功率、優惠碼剩餘量、關鍵
API 的 p99 延遲、資料庫連線池使用率、佇列積壓長度。CPU 正常但下單成功率掉到 60%，是
需要在三十秒內知道的事，而基礎設施的圖表不會告訴我。

活動期間安排人真的在線上盯著，不要只靠告警。事先講好誰有權按下降級開關 —— 在事故當下
才討論授權是來不及的。

## 活動後

保留完整的監控資料與日誌做復盤：實際尖峰是預估的幾倍、哪一層先出現壓力、哪些降級開關
真的被用到。把臨時放寬的設定（WAF 規則、副本數、限流閾值）收回去，別留著變成隱形成本。
這次的數據就是下次活動的基準值。

## 但書

以上是在不知道 AsiaYo 實際架構與流量基準的前提下的思路與優先順序。前面那三個問題的
答案會大幅改變工作重心：如果活動頁只是純行銷落地頁，這份清單的八成都不需要做，靜態化
丟上 CDN 就結束了。
