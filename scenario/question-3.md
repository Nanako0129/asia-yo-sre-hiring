# 情境實戰測驗 題目三：EC2 服務正常但無法 SSH 登入

> 試想有一項目運行於 AWS EC2 機器之上，已確認該服務仍然正常運行中，但由於不明原因導致
> 無法再次透過 SSH 登入確認狀態（已確認排除並非網路異常，亦非防火牆阻擋所導致）。
> 請簡易描述你將如何排查問題，並且讓服務恢復正常運作？考量的細節是什麼？如果可以，
> 請試著回答造成無法登入的可能的肇因為何？

## 這題的前提我不打算照單全收

題目說已排除網路異常與防火牆阻擋。我會把這句話當成待驗證的假設，而不是既定事實，
理由很單純：**連不進主機的人，沒有立場證明主機那一端是正常的。** 從外面能確認的通常
只有「ping 得通」或「Security Group 看起來沒問題」，這兩件事都不足以排除一整層。

我實際遇過一次：某台機器的 SSH 開在 2222，一次自動更新把 `sshd_config` 改回了 22，
而 22 已經被同機的 GitLab 佔著，於是 sshd 直接啟動失敗。從客戶端看就是連不上，
而它既不是網路異常、也不是防火牆阻擋 —— 但當下如果接受了「網路和防火牆都排除了」
這個前提，就會往完全錯誤的方向查。

## 客戶端已經告訴你答案在哪一層

在猜原因之前，先看 `ssh -vvv` 停在哪一步。不同的停法指向完全不同的地方：

| 卡在哪 | 代表什麼 | 往哪查 |
|---|---|---|
| `Connection refused` | 有東西回了 RST，網路是通的，只是沒有 process 在聽那個 port | sshd 沒起來，或沒 bind 到預期的 port |
| `Connection timed out` | 封包被默默丟掉，沒有任何回應 | SG、NACL、host 上的 iptables、路由，或機器已經無法回應 |
| 版本協商完成後卡在 KEX | TCP 通、sshd 活著，是演算法或封包談不攏 | KEX 演算法、MTU／PMTU |
| `Permission denied` | 交握成功，認證失敗 | 金鑰、`authorized_keys` 權限、SELinux、磁碟滿 |
| 認證通過後卻斷線或無回應 | 登入流程本身出問題 | 使用者 shell、家目錄、PAM、資源耗盡 |

`refused` 和 `timeout` 的差別特別重要，卻常常被跳過。前者已經證明網路是通的 ——
題目那句「排除網路異常」在這個情況下是對的，但推論方向反了：不是因為網路正常所以
要往別處查，是因為 RST 回得來，才知道網路正常。

## 不必等 SSH 修好才能進去看

地端機房遇到這種情況會直接用 VNC 或 IPMI 進去看。EC2 上對應的是三個東西，
其中一個是陷阱：

| 途徑 | 特性 | 什麼時候有用 |
|---|---|---|
| **SSM Session Manager** | agent 主動出站到 AWS，不需要任何入站 port，完全繞過 sshd | 最先試這個 |
| **EC2 Serial Console** | 真正的帶外，等同接上實體 console | 網路完全不通、或連 SSM agent 都死了 |
| EC2 Instance Connect | 推送臨時金鑰，最終仍由 instance 上的 sshd 驗證 | sshd 沒起來時它一樣進不去，別把它當備援 |

SSM 特別值得先試，因為它能在三十秒內把問題空間切成兩半：SSM 進得去而 SSH 進不去，
就同時證明了網路通、機器活著、問題出在 sshd 自己身上。前面那個 2222 的案例用這招
會立刻現形 —— 進去 `systemctl status sshd` 一看就知道它根本沒起來。

Serial Console 有前置條件：Nitro 世代機型、帳號層級要先啟用、而且要事先設好 OS 使用者
密碼。這些都得在出事之前準備好，臨時才想開通已經來不及了。

真的全部走不通時，最後手段是停機、把 root EBS detach 掛到另一台機器上改設定、再掛回去。
這招一定有效，但代價不小，而且有個容易忘記的副作用：**沒有 Elastic IP 的話，停機再開
public IP 會換掉**，所有白名單、DNS、監控設定都要跟著動。

## 「服務還活著」這個條件本身就是線索

有一整類故障的特徵剛好長這樣：**已經跑起來的 process 繼續跑，但系統開不了新的
session。** 題目給的條件（服務活著、登入不了）完全落在這個形狀裡。

- **root 分割區滿了**。sshd 寫不了 log、建不了 session。已經在跑的服務把檔案開著，
  完全不受影響。`df -h` 之外也要看 `df -i`，inode 用盡的症狀一模一樣但空間看起來還很多
- **PID 耗盡**。`kernel.pid_max` 或 cgroup 的 `pids.max` 撞頂，sshd 無法 fork 出新的子行程
- **file descriptor 耗盡**。系統層的 `fs.file-max` 或 sshd 自己的 limit 用完，`accept` 直接失敗
- **記憶體壓力**。機器還沒到 OOM，但已經在瘋狂 swap，新連線要等上好幾分鐘。從客戶端
  看是逾時，機器其實只是慢到不像話

最後這種在 metrics 上很好認：如果有 Grafana，直接看該機器的 memory、swap in/out、
load average 與 disk I/O，通常一眼就知道是誰把資源吃光了。這也是為什麼監控要涵蓋
主機層：應用程式的健康檢查會回你 200 OK，然後你登不進去。

## 那些「不算防火牆」的防火牆

多數人講「防火牆」時指的是 Security Group 和 NACL，但擋住連線的東西不只這兩個：

- **host 上的 iptables／nftables**。SG 放行不代表 OS 內也放行。這一層在雲上很容易被
  忽略，因為大家習慣把網路控制想成雲平台的事
- **fail2ban**。這個特別惡劣：連不上所以拼命重試，重試觸發了 ban，於是更連不上。
  防火牆完全正確地運作，只是把你當成了攻擊者
- **SELinux**。改了 sshd 的 port 但沒跑 `semanage port -a -t ssh_port_t -p tcp 2222`，
  sshd 會 bind 失敗。這跟我遇到的那次是同一個故事的另一個版本 —— 設定檔看起來完全正確，
  服務就是起不來，而原因不在設定檔裡
- **`/etc/hosts.deny`／TCP Wrappers**。老系統上還看得到

## 交握層與金鑰層

如果 TCP 通了但卡在交握，有兩個方向：

**後量子 KEX 的封包大小。** OpenSSH 9.x 開始預設啟用 `sntrup761x25519-sha512` 這類
混合式後量子演算法，它的公鑰超過 1KB，KEX 封包比傳統演算法大一個量級。碰上 MTU
或 PMTU 黑洞、或是有 bug 的中間設備，連線就會卡死在交握階段。特徵很好認：版本協商
已經完成，然後就沒有下文了。臨時解法是強制指定傳統的橢圓曲線演算法：

```bash
ssh -o KexAlgorithms=curve25519-sha256 user@host
```

能連上就確認是這個問題，接著去修 MTU 或中間設備。永久降級演算法不是解法。

**認證層的老問題。** `authorized_keys` 或家目錄權限被改動（sshd 對權限的要求很嚴，
群組可寫就會拒絕）、host key 因為重建機器而變更、金鑰對應的使用者被鎖定或 shell 被
改成 `/sbin/nologin`。這些用 `ssh -vvv` 配合機器上的 `/var/log/secure` 或
`journalctl -u sshd` 對照，通常很快就有答案。

## 恢復服務與事後處理

進得去之後，`sshd -t` 先驗設定檔語法，再 `systemctl restart sshd`。如果是設定被自動
更新覆蓋，把套件更新的行為一併處理掉，否則下次更新會重演。

真正要留下的東西是**第二條路**。這次會這麼棘手，根本原因是登入途徑只有 SSH 一條，
它一斷就什麼都做不了。事後至少要做到：

- SSM agent 裝好並確認 IAM role 正確，讓它成為常態可用的備援途徑
- Serial Console 的帳號層級開通與 OS 密碼事先設好
- 主機層監控涵蓋磁碟、inode、PID、fd
- 如果 SSH 開在非標準 port，把這件事寫進機器的設定管理，別讓自動更新有機會改掉它

至於題目問的可能肇因，依我的判斷排序：sshd 因設定被覆蓋或 port 衝突而沒有啟動、
磁碟或 inode 用盡導致無法建立新 session、host 層防火牆或 fail2ban 攔截、
資源耗盡造成連線逾時、以及交握階段的演算法相容性問題。第一項的機率最高，
而它剛好是「既非網路也非防火牆」的那一類。
